# Sawti 3.0.6 microphone selector fix

The operator reported that a microphone combination reverted to no selection. The cause was `renderPower` resetting the selector whenever the server's `microphone_plan` was empty. Status polling calls this every second, including while the operator is choosing an unconfirmed combination. The old UI also failed to populate the selector from a confirmed plan on page reload.

The actual UI script now keeps the pending choice across repeated renders in the same power/mode context. It synchronises the selector on initial load or when the confirmed plan changes. OFF, mode changes and power-epoch changes reset stale drafts. Confirming updates the displayed accepted plan immediately and invalidates status responses admitted before that confirmation. A session change during the modal prevents stale submission. No routing, input/arm state or transport command is changed by this fix.

Before the fix, new tests reproduced three failures: draft clearing during polling, missing confirmed selection on load and failure to reflect a new plan from another tab. After the fix, all 26 JavaScript checks passed, including the existing voice/OFF and uninstall checks. The 34 live HTTP checks passed in isolated simulation. Shell syntax and the packaged source inventory were checked. Python application logic was unchanged except the version; the previous release's 152-test Python result is historical and was not rerun for this UI fix.

These tests use DOM/network substitutes rather than Safari. On the Mac: finish recording, quit Sawti, install 3.0.6 from a new permanent Documents folder, launch it and refresh the browser page. Check the displayed version is 3.0.6. Switch ON, choose Podcast, select a microphone combination, wait several seconds and confirm it remains selected. Then explicitly confirm while idle and verify that the accepted inputs appear in the status text. Reopening the page should show that confirmed selection. OFF should still clear the plan.
